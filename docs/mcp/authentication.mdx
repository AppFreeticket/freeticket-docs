The tools you see depend on the credential the connection carries.

| Layer | Endpoint | Credential | Tools |
| --- | --- | --- | --- |
| Public (B2C) | `/mcp/public`, or `/mcp` without sign-in | None | `public_*`: discovery, availability, orders, ticket resend |
| OAuth 2.1 sign-in | `/mcp` | Access token issued after you sign in to FreeTicket | Public tools plus workspace tools. Only read tools with scope `read`. |
| Buyer session | `/mcp` | `X-Customer-Session` header | Adds the `customer_*` tools |
| Local stdio | Your machine | `FT_API_KEY` and other environment variables | The same tools, run locally |

In every layer, workspace tools act with **your role** in the target workspace, exactly like the [API](/guides/authentication#roles).

The hosted server doesn't accept a raw API key as a bearer token. A request with `Authorization: Bearer ft_live_…` gets `401 invalid_token`. Sign in with OAuth, or run the server locally over stdio.

## Public

No account and no setup. Use this layer for agents that help buyers: they search published events, read live availability, and create an order that returns a payment link for the buyer. The agent never processes the payment.

```text
https://mcp.appfreeticket.com/mcp/public
```

`/mcp` without a token also serves the public tools, and it lists the workspace tools so the assistant knows they exist. Anonymous traffic is limited to 120 requests per minute per IP, and over that the server answers `429` with `Retry-After`.

## OAuth sign-in

The server embeds an OAuth 2.1 authorization server. This is the default for chat clients like Claude and ChatGPT, which can't send custom headers:

<Steps>
  <Step title="Discovery">
    Calling a workspace tool without a token returns `401` with a `WWW-Authenticate` header (`scope="b2b"`) that points to `https://mcp.appfreeticket.com/.well-known/oauth-protected-resource` (RFC 9728). The client discovers the authorization server metadata from there (RFC 8414), and shows its sign-in prompt.
  </Step>
  <Step title="Client registration">
    The client registers itself automatically (dynamic client registration, RFC 7591), so there is no client ID or secret to fill in.
  </Step>
  <Step title="Sign in and approve">
    The consent page offers **Continue with FreeTicket**. You sign in with your normal account and approve, using the same device flow as `ft login`. There is no workspace to pick: the connection reaches every workspace your account does.
  </Step>
  <Step title="Token">
    The client receives an access token and a refresh token (authorization code with PKCE `S256`), and renews the access token without asking you again.
  </Step>
</Steps>

Access tokens last 1 hour. Refresh tokens last 30 days, rotate on every use, and the session is capped at 90 days from sign-in. After that you sign in again. Every refresh checks the underlying key with FreeTicket, so revoking it (in the dashboard or with `ft api-keys revoke`) ends the connection within the hour.

Under **Advanced options**, the consent page also lets you paste an API key by hand, and tie the connection to a single workspace.

## Read-only connections

Tick **Read only** on the consent page, or request the OAuth scope `read`, for an analysis-only connection. It lists only the tools marked read-only, so the assistant has no write tool to call. A key with `read` scope pasted under **Advanced options** has the same effect. Call `whoami` to see the scope of the connection.

## Local stdio

For CI, scripts and headless machines, run the server locally over stdio with an API key:

| Variable | Purpose |
| --- | --- |
| `FT_API_KEY` | An `ft_live_…` key. Create one with `ft api-keys create mcp-agent --scope read`, or use the account stored by `ft login`. |
| `FT_WORKSPACE_ID` | Optional. Pin the connection to one workspace. |
| `FT_READ_ONLY` | `1` registers only the read tools |
| `FT_CUSTOMER_SESSION` | Optional. A buyer session, which adds the `customer_*` tools. |

The package isn't published on npm, so build it from [the source repository](https://github.com/AppFreeticket/freeticket-mcp) and point your client at `node dist/index.js`. Prefer a read-only key (`ft login --read-only`) on shared machines.

## Choosing the workspace

- By default nothing is pinned. List and row-based report tools read **every workspace your credential reaches** and tag each row with `workspaceId` and `workspaceName`.
- Pass `workspace: ["<id>", …]` to narrow a list to some workspaces, or to one when you need to page deep. `"all"` is the same as leaving it out.
- Tools that act on one resource (get, create, update, delete…) run against your account's default workspace unless the connection is pinned.
- To pin the whole connection, fill in the workspace under **Advanced options** during OAuth sign-in, or set `FT_WORKSPACE_ID` over stdio.

Call the `whoami` tool to see your user, your workspaces and your role in each.

## Buyer sessions

The `customer_*` tools (a buyer's own tickets, membership, profile and addresses) are for integrations that already hold a buyer session. They appear only when the connection carries that session in the `X-Customer-Session` header, or `FT_CUSTOMER_SESSION` over stdio. The session is never passed as a tool argument, so it doesn't go through the model, and these tools send only the session, never your workspace key.

`merch_orders_lookup` and `customer_merch_orders` need both an enterprise service API key and the buyer session.
