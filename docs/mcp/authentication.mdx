The tools you see depend on the credential the client sends.

| Layer | Endpoint | Credential | Tools |
| --- | --- | --- | --- |
| Public (B2C) | `/mcp/public` | None | `public_*`: discovery, availability, orders, ticket resend |
| OAuth 2.1 sign-in | `/mcp` | Token issued after you sign in to FreeTicket | Public tools plus B2B tools for your workspaces |
| API key | `/mcp` | `Authorization: Bearer ft_live_xxx` | Public tools plus B2B tools for your workspaces |

In every layer, B2B tools act with **your role** in the target workspace, exactly like the [API](/guides/authentication#roles).

## Public

No account and no setup. Use this layer for agents that help buyers: they search published events, read live availability, and create an order that returns a payment link for the buyer. The agent never processes the payment.

```text
https://mcp.appfreeticket.com/mcp/public
```

## OAuth sign-in

The server embeds an OAuth 2.1 authorization server. This is the default for chat clients like Claude and ChatGPT, which can't send custom headers:

<Steps>
  <Step title="Discovery">
    An unauthenticated request to `/mcp` returns `401` with a `WWW-Authenticate` header that points to `https://mcp.appfreeticket.com/.well-known/oauth-protected-resource` (RFC 9728). The client discovers the authorization server metadata from there (RFC 8414).
  </Step>
  <Step title="Client registration">
    The client registers itself automatically (dynamic client registration, RFC 7591), so there is no client ID or secret to fill in.
  </Step>
  <Step title="Sign in and approve">
    The consent page offers **Continue with FreeTicket**. You sign in with your normal account and approve, using the same device flow as `ft login`. There is no workspace to pick: the connection reaches every workspace your account does.
  </Step>
  <Step title="Token">
    The client receives an access token and a refresh token (authorization code with PKCE `S256`), and renews the access token without asking you again.
  </Step>
</Steps>

Under **Advanced options**, the consent page also lets you paste an API key by hand, and tie the connection to a single workspace.

## API key

For clients that can send headers, such as Claude Code, Cursor, scripts and CI, pass a FreeTicket API key directly:

```http
Authorization: Bearer ft_live_xxx
X-Workspace-Id: <workspace-id>      # optional
```

Create a dedicated key with `ft api-keys create mcp-agent --scope read` (or `--scope write`). Prefer a `read` key for analysis-only agents: write tools then fail with `403 READ_ONLY_KEY` instead of acting. See [Authentication](/guides/authentication).

## Choosing the workspace

- By default nothing is pinned. List and row-based report tools read **every workspace your credential reaches** and tag each row with `workspaceId` and `workspaceName`.
- Pass `workspace: ["<id>", …]` to narrow a list to some workspaces, or to one when you need to page deep. `"all"` is the same as leaving it out.
- Tools that act on one resource (get, create, update, delete…) run against your account's default workspace unless the connection is pinned.
- To pin the whole connection, send `X-Workspace-Id` with an API key, or fill in the workspace under **Advanced options** during OAuth sign-in.

Call the `whoami` tool to see your user, your workspaces and your role in each.

## Buyer sessions

The `customer_*` tools (a buyer's own tickets, membership and profile) are for enterprise integrations that already hold a buyer session. They require an enterprise service API key in addition to the buyer's session token. Ordinary workspace keys can't use them.
